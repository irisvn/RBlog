# UI guidelines

The rules every RBlog admin screen follows. They match the RustCMS admin shell the blog runs in
(its Users, Roles and Audit pages are the reference), so that RBlog reads as one product with
the panel. A screen that needs something these rules do not cover adds the rule here first, in
the same change, with the owner's agreement.

Origin: adapted from RDockPanel's `docs/ui-guidelines.md` (approved 2026-10-20), the design system
shared by the owner's RustCMS applications. Adopted for RBlog on 2026-10-23.

**Scope: the admin panel only.** RBlog is an admin application. The public blog site (what
readers see) is out of scope for now: the owner will design it later, and these rules do not
apply to it.

## 0. Where these rules apply

- **Resources, forms, tables, actions and settings pages are generated by RustCMS** from Rust
  (`src/admin/`). They already follow the shell. What RBlog chooses there must still follow
  these rules:
  - labels, words and translations (§9);
  - which fields are searchable, sortable and filterable, and the default sort;
  - action names, which actions are destructive and need confirmation, and status words (§4).
  The shell draws these screens, so §2 (page frame) and §7 (`rblog/lib/` components) do not
  apply to them. Check them against what the browser shows: §8 (phone, dark mode) and §9 (words).
- **Custom React pages** (`resources/admin/src/rblog/`) follow every section below. Write one
  only when a resource cannot express the screen.
- **Slots and cells** live inside a shell page. They follow §1 (foundations), §3–§6 for the
  controls they contain, §8 and §9, but never draw a page frame (§2).
- **HTML template pages** (`resources/views/admin/`) use the RustCMS `rc-*` classes (`rc-stack`,
  `rc-grid`, `rc-card`, `rc-title`, `rc-muted`, `rc-table`, `rc-badge`, `rc-link`, `rc-meter`)
  and the same tokens.

## 1. Foundations

### Building blocks
- React pages are built with the kit `@rustcms/admin-sdk/ui` and RBlog's own components in
  `resources/admin/src/rblog/lib/` (§7).
- Do not add a CSS class for something the kit or `lib/` already draws. A new shared component
  goes in `lib/`, with a line in §7.

### Color
- **Theme tokens only**:
  - surfaces and text: `--background`, `--foreground`, `--card`, `--muted`,
    `--muted-foreground`, `--border`, `--ring`;
  - roles: `--primary`, `--primary-foreground`, `--secondary`, `--destructive`,
    `--destructive-foreground`, `--success`, `--warning`.

  Never write a literal color in a component or in CSS. Colors are set only in `Theme` (hex,
  with a `dark(…)` palette) in `admin_panel_provider.rs`, or at run time through branding.
- **Status tones** use the RustCMS tokens, so that they follow the theme in light and dark:

  | Tone | Token |
  |---|---|
  | ok | `--success` |
  | busy | `--warning` |
  | bad | `--destructive` |
  | off | `--muted-foreground` |

  RustCMS defaults `success` and `warning` to grays (in dark mode both are `#d4d4d8`), so the tones
  would be indistinguishable. The theme in `admin_panel_provider.rs` therefore **must** set them
  for both schemes, for example:

  ```rust,ignore
  Theme::new()
      .color("success", "#15803d").color("warning", "#b45309")
      .dark(|dark| dark.color("success", "#4ade80").color("warning", "#fbbf24"))
  ```

  Each tone must keep at least 3:1 contrast against `--card` in both themes. Check this when the
  theme or branding changes.
- **Status colors only fill a dot**, or a segment of a bar beside its written value. The label
  beside the dot stays in the normal text color, and the state is always written: never shown by
  color alone.
- **Alerts** use the kit `Alert` in its `default` variant, with a 16px icon from `lib/icons` in
  the tone's color, and normal text. The `destructive` and `warning` variants tint the border,
  background and text of the whole box, so they are not used.
- **Primary** (the brand color) is for the one main action of a view and for the selected
  state. Nothing else is colored.

### Type
The shell's font (`--font-sans`, the system UI face), five sizes, three weights:

| Token | Size / line | Use |
|---|---|---|
| `xs` | 12px / 16px | table headers, badges, captions, help text under a field, small buttons |
| `sm` | 14px / 20px | **the default UI text**: table cells, form labels and inputs, descriptions, buttons |
| `base` | 16px / 24px | section titles (600), long reading text (rare) |
| `lg` | 20px / 28px | metric values (tiles, 600, tabular numbers) |
| `2xl` | 24px / 32px | the page title only (shell `h1`, 600) |

- Weights: 400 for text, 500 for labels and the table cells that name a row, 600 for titles
  and values.
- One monospace face, `ui-monospace, SFMono-Regular, Menlo, monospace`, at 13px (class
  `rblog-mono`). It is for values that are code: slugs, URLs, ids, hashes, file names, JSON.
  Never size it with `em`.
- Use sentence case everywhere ("New post", not "New Post"). Uppercase only for the page eyebrow
  (12px, 500, letter-spacing 0.05em).
- Numbers that line up use `tabular-nums`.

### Space and shape
- A 4px grid: gaps of 4, 8, 12, 16, 24 and 32px only.
- Spacing:
  - the page keeps the shell's padding;
  - sections are 24px apart;
  - inside a section, blocks are 16px apart, with a padding of 20px (24px from 640px up), as in
    the shell's form sections.
- Radius: sections and dialogs `calc(var(--radius) + 4px)`; buttons, inputs, badges and tiles
  `calc(var(--radius) - 2px)`. Nothing else.
- Borders are 1px `--border`. The only shadow is the shell's `shadow-xs`, on sections.
- No nested cards: separate a block inside a section by space or a divider, not by another
  border.

## 2. Page layout

Every page has the same frame, top to bottom:

1. **Page header** (`PageHeader`): eyebrow, title, description, and the actions on the right.
   - Eyebrow: the kind of page (`Content`, `Media`, `Settings`), as plain text. There is no
     breadcrumb: the sidebar and the page's own links lead back.
   - Title: the thing itself (`Posts`, or the post's title). A post's status badge sits after
     its title.
   - Description: one 14px muted sentence, only where it helps.
2. **Tabs**, when the page has several views: kit `Tabs` inside `ScrollTabs`, which keeps the tab
   list on one row and scrolls it sideways on a narrow screen. Each `TabsList` has an
   `aria-label`.
3. **Content**: a vertical stack of sections, 24px apart (`Stack`).

Nothing sits between the header and the tabs, or between the tabs and the first section.

The shell draws its own heading above every page. A page that draws its `PageHeader` hides the
shell's heading with `props.title(null)`, which keeps it for screen readers. Otherwise the title
shows twice. Do this in one place, the `Page` wrapper of `lib/` (§7), never page by page. A page
that keeps the shell's heading names its sub-paths with `props.title(text)`.

### Sections
- A section is a `Section`: a card with a header (a 16px/600 title, an optional description and
  actions on the right) and a body.
- A section holds one topic. A long form is several sections, not one. A form that must save in
  one go groups its fields under `h3` sub-headings (14px/600, after a divider) inside its one
  section.
- A page with a single table may use the table's card as its only section.

## 3. Buttons

### Sizes
| Where | Size |
|---|---|
| Page header actions, form submit, dialog footer | `default` (36px) |
| Section header actions, toolbars, filters | `sm` (32px) |
| Table rows and lists | `sm`, or an `IconButton` (32px square) with a tooltip and an `aria-label` |

The kit's `size="icon"` is 36px. `IconButton` narrows it to 32px (`size-8`) so that it lines up
with `sm` buttons. Its `aria-label` names the target ("Delete image cover.jpg").

`lg` is not used. A button's size depends only on where it is, never on how important it feels.

### Variants
| Variant | For |
|---|---|
| `default` (primary) | the one main action of a page header, a form or a dialog. At most one per region. |
| `outline` | the other actions beside it |
| `ghost` | row actions, Cancel, icon buttons, menu triggers inside tables |
| `destructive` | the confirm button of a destructive dialog, and the Danger zone's button. Never in a list or table row. |
| `link` | an action inside a sentence |

### Labels
- Verb first, in sentence case, with no `+` or other glyph: `New post`, `Add tag`, `Publish`.
- `New …` creates something on its own (a post, category, user, token). `Add …` attaches
  something to its parent (a tag to a post, an image to a gallery).
- An icon is optional: 16px, before the label, from `lib/icons` (§7). No emoji and no text
  arrows (`▾`, `↗`, `✎`).
  - A menu trigger gets the chevron icon.
  - An outside link (for example "View on site") gets the external-link icon.

### Order and placement
- Actions sit in right-aligned groups, with the primary button last (rightmost), after any `⋯`
  menu: `[Preview] [⋯] [Publish]`. Dialog footers are `[Cancel (ghost)] [Primary]`.
- On a phone, the header keeps the primary and `⋯`. The actions it hides move into `⋯`, with the
  same permission and busy-state rules: disabled with a reason, never removed silently.
- Show an action only when it applies to the current state: `Publish` for a draft, `Unpublish`
  for a published post.
- A row shows at most two actions. Anything more goes into a `⋯` menu (`RowActions`).
- In generated lists and record pages (RustCMS 0.10.1), the server decides which actions a row
  offers: declare each with `visible_when` from the rule that owns its state (posts:
  `publishing::Transition::applies`), mark the one frequent action `.primary()` (Publish), and
  `.destructive()` the ones that take something away from readers (Unpublish). RustCMS draws the
  primary one labelled and the rest in the row's `⋯` menu, destructive ones last after a
  separator; View, Edit and Delete keep their icon buttons. A form dialog's button names the
  action without the ellipsis (`.submit_label("Schedule")`).
  Destructive items go last in that menu, after a separator, marked `destructive`.
- Links that look like buttons use `buttonVariants()`, never a hand-made class.

## 4. Data: tables, lists, metrics, status

- **A collection with two or more attributes is a table**: a kit `Table` in a `Section` (or a
  `TableCard`).
  - The header is 12px muted on `--muted`; cells are 14px with 12px padding.
  - The name column is 500 weight, with any secondary text under it in 12px muted.
  - Numbers and sizes are right-aligned, with `tabular-nums`.
  - The actions column is last, right-aligned, with a fixed width. Put the layout in a `div`
    inside the cell, never on the `td` itself.
  - Long values (slugs, URLs, file names) are truncated with an ellipsis and a tooltip that shows
    the whole value. Copyable values get a copy icon button.
  - On a narrow screen the table scrolls sideways inside its card. Columns hide only by a class
    the table chooses, never by position: `rblog-hide-md` when the table's card is narrower than
    640px (a tablet beside the sidebar), `rblog-hide-sm` on a phone (640px wide or less). The row
    actions column always stays, and a hidden value that matters (an expiry) stays in a tooltip.
- **Pagination**:
  - 25 rows a page, in a stable order: newest first, unless the column says otherwise.
  - A footer `1–25 of 132` with Previous and Next.
  - Filters are kept in the URL, so that a link reopens the same view. A changed filter goes
    back to page 1.
  - "No results" (a filter matched nothing, with a Clear filters action) differs from "empty"
    (nothing exists yet).
  - A history the server keeps only in part says so (`Latest 100 actions`).
- **Row details**: the name cell links to the item's page or edit form. A row shows one labeled
  frequent action, plus `⋯`. Icon-only buttons are only for actions that every row has (for
  example Preview), each with a tooltip and an `aria-label`.
- **Hidden rows** are never hidden silently. A filter that hides some rows (archived posts) is a
  visible toggle with the count (`Show 8 archived posts`).
- **A list** (`List`) is for a collection with one attribute and an action, such as API tokens.
  If it grows a second column, it becomes a table.
- **Facts** (label above value) show the properties of one object: labels 12px muted, values
  14px, monospace only for values that are code.
- **Metric tiles** (`Metric`, and the RustCMS dashboard widgets): the label is 12px muted, the
  value 20px/600, with an optional 12px muted sub-line. Tiles are not cards inside cards: inside a
  section they form a row, divided by space.
- **Status** (`StatusBadge`): a dot and a word, in the kit `Badge` (neutral, `color="gray"`). The
  four **tones** are shared. The **word** belongs to the kind of thing:

| Kind | ok | busy | bad | off |
|---|---|---|---|---|
| Post, Page | Published | Pending review, Scheduled | — | Draft |
| Comment (if built) | Approved | Pending | Spam | Hidden |
| Background job (import, export, mail) | Done | Queued, Running | Failed | — |
| Media upload | Uploaded | Uploading, Processing | Failed | — |
| API key (Content API) | Active | — | — | Expired |

Raw values (enum names, error codes) stay available in a tooltip or a detail view, never as the
badge. The mapping from server states to words lives in one place, `lib/status.ts`.

## 5. Forms

- **Fields**: the label is above the field (14px/500), the help text below it (12px muted), and
  the error below that (12px `--destructive`). A field's width follows its content: titles and
  slugs are full width, numbers narrow.
- **Columns**: two columns from 768px up for short related fields; one column below 768px.
- **Saving**: the submit button closes the section, bottom right. A form that saves shows a
  `Saved` toast and stays where it is.
- **Adding to a list**: adding a row to a list or table opens a **dialog** (`Add tag`), never an
  inline form above the list. Small inline edits (a toggle, a select) save on change, with a
  toast.
- **Native controls**: none raw. File pickers are a `Button` over a hidden input
  (`FilePicker`); colors are a swatch plus a hex input (`ColorField`); checkboxes and switches
  come from the kit.
- **Editors** (posts and pages, RustCMS 0.10.2): `Form::width(FormWidth::Full)` with one
  `Split`, so that the text uses the width of the window.
  - **Main column**: title, then the slug right under it (`TextInput::prefix`: `/posts/` or
    `/`), body, excerpt, and SEO last in a folded section (`Section::collapsible(true)`).
  - **Aside**: compact sections (`Section::compact`) for the details: Publishing (status and
    publish date read-only, author), Cover image, and for posts Organize (category, tags,
    featured). The workflow actions stay in the page header, never in the aside.
  - Other forms keep the default width unless a long text field needs more room.
- **Blog fields**:
  - **Slug**: generated from the title as ASCII without diacritics (`xin-chao-viet-nam`),
    editable, shown in `rblog-mono`. It is unique, and a clash is a field error.
  - **Body**: RustCMS rich text (the guide's `admin/media.md`). It is a JSON document column,
    with `Field::column(…).rich_text()` and `RichEditor`, never a text column. The limits are
    256 KiB of JSON, 10,000 elements, 16 levels and 100 images. A refusal is a 422 field error.
  - **Publish date**: an instant, edited with the RustCMS `DateTimePicker`, which edits **in
    UTC** and labels the field UTC. The help text says so ("Times are in UTC"). Editing in local
    time would need a custom widget that converts zones; build one only with the owner's
    agreement.
- **Secrets** follow their kind:
  - **Write-only** (SMTP passwords, integration keys): the field says `Kept` and stays empty.
    Typing replaces the value, and an explicit `Remove` clears it. There is never a `Show`.
  - **Shown once** (API tokens): one view with Copy and "it is not shown again".
- **Unsaved changes and conflicts**: a form with unsaved changes says so before the user leaves
  it. A save that is rejected because someone else changed the record explains why and offers
  to reload.

## 6. Feedback

| Situation | Use |
|---|---|
| An action succeeded | a short toast (`props.toast`): `Published`, `Token revoked` |
| An action failed | a toast with the error, or an `ErrorNote` in the form that caused it |
| A lasting state the user must know | an `Alert` at the top of the section it concerns (one size: 14px) |
| Confirming something destructive or disruptive | `ConfirmDialog` (destructive button; a typed name for the irreversible, such as deleting a category with posts) |
| Nothing to show yet | `EmptyState`: one 14px line, an optional 12px hint and an optional action, centered in the section |
| Loading a whole page | kit `Loading` |
| Loading a block of known shape | kit `Skeleton` of that shape, so that nothing jumps |

`window.alert`, `window.confirm` and `window.prompt` are never used.

### Work that takes time (imports, exports, bulk actions, mail, image processing)
- The button that starts it shows its pending label (`Importing…`) and stays disabled until the
  server answers, so there is no double submit.
- The answer is "accepted", not "done": the toast says `Import queued`, with a link to it.
- Its progress lives where it belongs, with a busy status. A dropped stream shows
  `Reconnecting…`, then the last state.
- Waiting for something to come back has a time limit. Past it, an `Alert` says what to check and
  offers to retry.

### Dialogs
- Three widths, through the kit `Dialog`'s `className`: compact 440px (confirmations), form 560px
  (most forms), wide 880px (previews, long forms). Taller content scrolls inside the dialog.
- A dialog is labelled by its title.
- Every dialog has a visible `ghost` Cancel or Close in its footer.
- Focus:
  - it starts on the first field, or on Cancel for a confirmation;
  - it returns to the button that opened the dialog;
  - a failed submit focuses the first field in error, which is linked to its message
    (`aria-describedby`).
- Busy labels say what is happening ("Saving…"). While saving, `closeDisabled` blocks the close
  button and Escape.

## 7. Shared components (`resources/admin/src/rblog/lib/`)

Their CSS classes use the `rblog-` prefix. Create each component when the first page needs it.
`../rust-panel/resources/admin/src/rdockpanel/lib/` is a reference implementation: adapt it (prefix,
tokens), do not import from it.

| Component | What |
|---|---|
| `Page` | the page frame: `PageHeader` (eyebrow, title, description, actions) and content; hides the shell's heading (`props.title(null)`) |
| `Stack` | the vertical 24px rhythm of a page's sections (also inside a tab) |
| `Section` | a card with a header (title, description, actions) and a body |
| `ScrollTabs` | the kit tabs on one row that scrolls sideways |
| `TableCard` | a `Section` whose body is a kit `Table`, with a toolbar and an empty state |
| `RowActions` | up to two ghost buttons and a `⋯` menu |
| `IconButton` | a `ghost` 32px icon button with a tooltip and an `aria-label` |
| `StatusBadge` | a dot and a label from the status vocabulary (§4, `status.ts`) |
| `Metric` | the metric tile |
| `Facts` | the label/value grid |
| `EmptyState` | the empty line, hint and action |
| `ConfirmDialog` | the confirmation dialog, with an optional typed confirmation |
| `FilePicker`, `ColorField` | the styled file and color inputs |
| `icons` | the one icon set (Lucide shapes, 16px, stroke 2, `currentColor`) |
| `i18n`, `format` | translations, and number, date and size formatting on `Intl` |

## 8. Phone and dark mode

- Every page works at 390px wide, with no sideways page scroll:
  - tabs scroll sideways in one row;
  - page header actions wrap under the title, and beyond two, the rest go into a `⋯` menu;
  - grids become one column.
- Every page works in light and dark mode, with colors only from tokens (§1). Check both.
  Branch on `useColorScheme()` only when CSS variables cannot do it.

## 9. Words and formats

- Name things as editors know them: Post, Category, Tag, Author, Media, Draft. Buttons put the
  action first.
- Every string goes through `t()`, with its Vietnamese translation in the same change:
  - extension strings in `lib/i18n.ts` (`registerTranslations`);
  - server-side labels in `lang/vi.toml`;
  - every new server validation message has a translation template.

  Vietnamese runs about a third longer, so check labels and buttons at 390px in Vietnamese.
- Numbers, percentages and dates go through shared helpers on `Intl.NumberFormat` and
  `Intl.DateTimeFormat`, in the user's locale. File sizes are 1024-based, written KB, MB and GB.
  A relative time ("2 hours ago") has the absolute time, with its time zone, in a tooltip.

## 10. Checklist for a new or changed screen

For a custom page, every item. For a generated resource screen, a slot or a cell, the items §0
lists for it.

- [ ] `Page` (eyebrow, title, the shell's heading hidden); tabs right under it; sections in a
      `Stack`.
- [ ] Buttons: size by place, one primary per region, no `+`, no glyphs or emoji.
- [ ] Collections in `TableCard` (25 rows a page), row actions in `RowActions`, statuses in
      `StatusBadge`.
- [ ] Empty, loading and error states drawn with the shared components.
- [ ] No `window.confirm`/`alert`/`prompt`; destructive actions in `ConfirmDialog`.
- [ ] No new CSS class without need, no literal color, no `style=`; sizes from the type scale;
      alerts in the `default` variant with a tone icon; status tones distinct in both themes.
- [ ] Long work shows pending, queued and done states; dialogs have the right width and focus.
- [ ] Every string translated (English and Vietnamese).
- [ ] Checked with real screenshots at 1440px, 768px and 390px, in light and dark, in English
      and Vietnamese.
